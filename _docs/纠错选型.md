# 中文纠错选型：LightCorrector vs T5 GGUF Q8_0

## 背景

ASR 输出的文本需要纠错后处理。当前项目有两类需求：

1. **流式实时纠错**——`StreamingRunner` 的 `Partial`/`Committed` 事件，要求 <10ms 延迟
2. **离线精准纠错**——`transcribe_batch`、录音结束后、server `/api/transcribe`，可接受 100ms+ 延迟换取更高纠错质量

现有方案只有 `LightCorrector`（拼音 + bigram），覆盖场景 1 但场景 2 的语义级纠错能力不足。本文档分析接入 `mengzi-t5-base-chinese-correction` GGUF Q8_0 作为可选重纠错后端的方案。

## 两种方案对比

| 维度 | LightCorrector（现有） | T5 GGUF Q8_0（新增） |
|------|----------------------|---------------------|
| 原理 | 拼音映射 + bigram 转移概率 | 神经网络 seq2seq 生成 |
| 模型体积 | 0（450KB `include_bytes!` 嵌入二进制） | 264 MB（外部 `.gguf` 文件） |
| 延迟 | <1ms（纯查表 + 局部分词） | ~100-500ms（自回归生成，CPU） |
| 纠错能力 | 同音字、拼音混淆（zh/z、in/ing 等南方口音） | 语义级，可改写句子结构 |
| 内存占用 | ~30MB | ~500MB（264MB 权重 + 推理中间张量） |
| 外部依赖 | 无 | candle-core + candle-transformers（纯 Rust） |
| 加载方式 | 编译期嵌入，启动即用 | 运行时懒加载（`OnceLock`，首次调用约 1-2s） |

### 为什么不替换 LightCorrector

1. **延迟差 3 个数量级**——流式场景不能容忍 100ms+ 纠错，LightCorrector 仍是流式首选
2. **零依赖零体积**——嵌入式 / 最小化部署仍可用
3. **264MB 外部文件**——不是所有用户都需要语义级纠错

### 为什么选 GGUF 而非 ONNX

详见 [`scripts/export_mengzi_t5_onnx.md`](../scripts/export_mengzi_t5_onnx.md) 的关键决策分析。核心原因：

| 格式 | 体积 | 原因 |
|------|------|------|
| 原模型 safetensors (FP32) | 946 MB | 仅权重，推理逻辑在 PyTorch 代码 |
| ONNX INT8（3 文件） | 615 MB | 静态图导致 decoder 权重重复存 2-3 份 |
| **GGUF Q8_0** | **264 MB** | 权重只存 1 份（共享 embedding 去重），block-wise 量化更高效 |

GGUF 比 ONNX INT8 小 57%，且 candle 有现成的 `quantized_t5` 实现，无需手写推理逻辑。

## 接入方案

### 架构：双后端，配置切换

不替换 LightCorrector，而是新增 `T5Corrector` 作为可选的「重纠错」后端，通过配置开关切换。

```
crates/asr/src/
├── corrector.rs          # 现有 LightCorrector（不动）
├── corrector_t5.rs       # 新增：T5 GGUF 纠错器
└── pipeline.rs           # 修改：按配置选择 corrector
```

### Rust 依赖

`crates/asr/Cargo.toml` 新增：

```toml

```

纯 Rust crate，无 C++ 依赖，跨平台编译无坑（和 ort 的 download-binaries 一样省心）。

### 核心代码骨架

参照 candle 的 [quantized-t5 示例](https://github.com/huggingface/candle/blob/main/candle-examples/examples/quantized-t5/main.rs)：

```rust
// crates/asr/src/corrector_t5.rs
use candle::{Device, Tensor};
use candle_transformers::{generation::LogitsProcessor, models::quantized_t5 as t5};
use tokenizers::Tokenizer;

pub struct T5Corrector {
    model: t5::T5ForConditionalGeneration,
    tokenizer: Tokenizer,
    decoder_start_token_id: u32,
    eos_token_id: usize,
}

impl T5Corrector {
    /// 从 ~/.octopus/models/mengzi-t5-base-chinese-correction-gguf/ 加载
    pub fn new(gguf_path: &Path, tokenizer_path: &Path) -> Result<Self> {
        let device = Device::Cpu;
        let config = t5::Config {
            use_cache: true,  // 启用 KV cache，续步快
            ..serde_json::from_str(&fs::read_to_string(config_path)?)?
        };
        let vb = t5::VarBuilder::from_gguf(gguf_path, &device)?;
        let model = t5::T5ForConditionalGeneration::load(vb, &config)?;
        let tokenizer = Tokenizer::from_file(tokenizer_path)?.into();
        Ok(Self { model, tokenizer, ... })
    }

    /// 纠错：text → tokenize → encode → 自回归 decode → detokenize
    pub fn correct(&mut self, text: &str) -> Result<String> {
        let tokens = self.tokenizer.encode(text, true)?.get_ids().to_vec();
        let input_ids = Tensor::new(&tokens[..], &device)?.unsqueeze(0)?;
        let encoder_output = self.model.encode(&input_ids)?;

        // 自回归生成
        let mut output_ids = vec![self.decoder_start_token_id];
        for _ in 0..128 {  // max_length
            let decoder_input = Tensor::new(output_ids.as_slice(), &device)?.unsqueeze(0)?;
            let logits = self.model.decode(&decoder_input, &encoder_output)?.squeeze(0)?;
            let next_token = logits.argmax(D::MinusOne)?.to_vec1::<u32>()?[0];
            if next_token as usize == self.eos_token_id { break; }
            output_ids.push(next_token);
        }
        self.tokenizer.decode(output_ids, true)
    }
}
```

### 场景适配

| 场景 | 推荐 corrector | 理由 |
|------|---------------|------|
| 流式 `StreamingRunner`（Partial/Committed） | LightCorrector | <10ms 延迟要求，T5 的 100ms+ 会造成卡顿 |
| 离线 `transcribe_batch` | T5Corrector（如启用） | 可接受延迟，换取语义级纠错质量 |
| Desktop 录音结束后 | T5Corrector（如启用） | 一次性纠错，延迟不敏感 |
| Server `/api/transcribe` | T5Corrector（如启用） | 离线接口，质量优先 |

**流式不接入 T5**。`streaming_runner.rs` 继续用 LightCorrector，T5 仅用于离线路径。

## 风险点

1. **candle-transformers 版本兼容**——`quantized_t5::Config` 结构需要和 mengzi-t5 的 `config.json` 字段对齐（`feed_forward_proj: "gated-gelu"` 等）。如果 candle 的 Config 缺字段需手动补
2. **tokenizer 对齐**——candle 示例用 `tokenizers` crate 从 `tokenizer.json` 加载，项目已有此依赖（`crates/asr/Cargo.toml` 的 `tokenizers = "0.21"`），可直接复用。注意版本是否和 candle 要求一致
3. **首次加载延迟**——264MB GGUF 加载到内存约 1-2 秒，用 `OnceLock` 全局单例懒加载，只在首次纠错时触发
4. **candle crate 版本**——candle-core 和 candle-transformers 需同版本，且和当前 ort 依赖无冲突（ort 用 ndarray 0.17，candle 有自己的 tensor 体系，不交叉）
